# Subly — личный кабинет управления подписками SaaS

## О проекте

Проектирование личного кабинета для SaaS-сервиса, который позволяет пользователям управлять подписками: просматривать активные, менять тариф, отключать подписку и отслеживать платежи. Цель — снизить нагрузку на поддержку и сделать управление подписками прозрачным для клиента.

## Проблема и цель

До внедрения личного кабинета пользователи вынуждены обращаться в поддержку для смены тарифа или отключения подписки. Это создаёт очередь обращений, увеличивает время ответа и повышает риск ошибок при ручной обработке.

**Цель:** спроектировать ЛК, который закрывает ключевые сценарии самообслуживания и снижает количество обращений в поддержку.

## Моя роль

Системный аналитик:

- анализ стейкхолдеров и их влияния на требования;
- формализация User Stories, Use Cases и Job Stories;
- моделирование бизнес-процессов «как есть» (as-is) и «как должно быть» (to-be) в BPMN 2.0;
- проектирование UML-диаграмм (классов, последовательностей);
- спецификация REST API для ключевых операций;
- подготовка проектной документации к передаче в разработку.

## Ключевые аналитические решения и компромиссы

### 1. Приоритизация стейкхолдеров

Построена матрица «влияние / интерес». Ключевые стейкхолдеры: **пользователь** (хочет быстро управлять подпиской) и **финансовый отдел** (требует прозрачности списаний и возвратов). Это определило приоритет функций: сначала — смена тарифа и отключение, затем — история платежей.

### 2. Моделирование процессов: as-is vs to-be

Для смены тарифа и отключения подписки построены BPMN-модели в двух состояниях:
- **As-is:** пользователь звонит в поддержку → оператор вручную меняет тариф → риск ошибки и задержки.
- **To-be:** пользователь сам меняет тариф в ЛК → система пересчитывает стоимость и инициирует платёж.

**Компромисс:** to-be требует интеграции с платёжным шлюзом, но снимает нагрузку с поддержки и ускоряет операцию с часов до минут.

### 3. Формализация требований через Job Story

Вместо классических User Stories для сложных сценариев использованы **Job Stories** (формат «Когда [ситуация], я хочу [мотивация], чтобы [ожидаемый результат]»). Это позволило точнее описать контекст, в котором пользователь принимает решение о смене тарифа.

### 4. Проектирование API под сценарии

REST API спроектирован не «по сущностям», а **под ключевые пользовательские сценарии**: инициация платежа при смене тарифа, обработка успешного платежа, оплата со скидкой, обновление подписки. Для каждого метода определены входные параметры, статус-коды и диаграмма последовательности.

## Результаты и эффект

- Выявлены и приоритизированы стейкхолдеры, определены их требования к ЛК.
- Формализованы ключевые сценарии: просмотр активных подписок, смена тарифа, отключение подписки, оплата.
- Спроектированы BPMN-модели as-is и to-be, показывающие эффект автоматизации.
- Построены UML-диаграммы классов и последовательностей.
- Специфицирован REST API для интеграции с платёжным шлюзом.
- Подготовлена часть проектной документации, готовая к передаче в разработку.
